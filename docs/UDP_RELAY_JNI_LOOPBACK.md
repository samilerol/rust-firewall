# Native UDP relay → JNI → bounded Java TUN queue (loopback test)

This is an **integration test only**, with real local UDP I/O to **127.0.0.1** and an echo server created by the host-JVM test. It exercises the existing `UdpRelay` with a test Java `protect(int)` callback through `AndroidVpnProtector`, sends a checksummed IPv4 datagram from the Rust encoder, receives the loopback UDP payload, checks original-flow association and the **current reverse-direction policy**, then submits the returned full IP/UDP datagram via JNI into Java `TunEgressQueue`. Java's owner thread drains to an in-memory byte sink. No Android TUN descriptor is created or written.

The Rust test policy defaults to **Deny**. It explicitly allows only the fixed synthetic client (`10.111.0.2:41234`) to `127.0.0.1:<test-server-port>` over UDP. A separate reverse-direction rule is required for a reply to reach the queue. Without that rule, the relay rejects the reply and the Java queue stays empty. The test also checks refused/exceptional platform protection and invalid arguments. A fake Java protector returns success only under the deliberate host-JVM test setup; **never use a fake protector on actual Android**.

This test is not a shipping traffic path: `NativeCore.probeUdpRelayLoopback` remains a test-only callable surface, is never invoked from `DiagnosticVpnService`, and has a hard loopback destination, bounded polling, two-flow budget and 1280-byte MTU. It does not assert real Android `VpnService.protect`, upstream WAN reachability, DNS, network changes, IPv6, TCP, packet source attribution, VPN session revocation or any device-level leak protection. Future production code must use an independent, lifecycle-owned dispatcher with no general-purpose packet-injection JNI endpoint; only authorized tracked responses may enter the egress queue. See issue #9.

# Android forwarding session kernel (not wired to TUN or JNI)

`netscope_android::forwarding_session::ForwardingSession<U, T>` (unix only) bundles a `UdpRelay`, a `TcpRelay` and the combined readiness wait behind one single-threaded object. It owns no TUN, no JNI handle and no `VpnService`; those remain unimplemented and the existing `DiagnosticVpnService` still drops every packet. It supersedes the UDP-only `UdpSession` as the intended adapter core but does not replace it yet.

- **Default deny.** A new session denies every TCP and UDP packet without protecting a socket. `update_rules(Vec<ContextRule>)` always uses a default action of Deny, validates once so the two relays cannot diverge, and a valid update revokes every existing flow in both relays; an invalid update changes nothing.
- **Driving it.** Feed each packet read from the TUN to `handle_packet(packet, &Context)`, where the adapter supplies the uid/network it resolved for the flow (recorded when the flow is created). Then call `service(max_wait)` in a loop: it waits for upstream readiness or the relays' next deadline (`event::wait_ready`), services both relays and returns up to 64 packets for the TUN writer. `Backpressure` from `handle_packet` means re-submit the same packet after the next `service`. ICMP, fragments and extension headers return `Packet(..)` errors; nothing is silently accepted.
- **One clock.** The constructor takes a monotonic millisecond `Clock`; the session reads it before and after each wait and clamps it so it never goes backwards (the relays reject reversed time). Handing the relays two different time sources is therefore impossible through this API.
- **Failure isolation.** A reply the policy now denies or a vanished flow drops only that flow and is not reported by `service`; a TCP client whose flow is discarded gets a RST from the relay.
- **Terminal revoke.** `revoke` drops all flows and sockets and rejects every later call. The caller must separately revoke the platform protector and stop its workers.
- **Initial limits (unmeasured on any device):** UDP 64 flows / 30 s idle; TCP 128 flows, 16 KiB stream buffers, 16 pending handshakes, 64 flows per uid, 10 s connect timeout and 30 min idle; MTU 1500.

Evidence: unit tests with real loopback sockets and an explicitly marked counting protector: default deny with zero protection calls, UDP gated by uid with the reply returned by `service`, a hand-built TCP SYN admitted for one uid and answered with a SYN-ACK only after the upstream connect, a refused connect answered with RST and never a SYN-ACK, atomic rule updates and terminal revoke, and a backwards clock never reaching the relays (a mutation check fails that test). The TCP data path is covered by the transport tests, not here.

**Not implemented or verified:** JNI lifecycle and handle ownership, real `VpnService` binding and TUN read/write loops, the Android `getConnectionOwnerUid` lookup that would produce the `Context`, synchronization of protector revocation with session cancellation, IPv6 on a real network, emulator or physical-device behavior (no Android SDK or device was available), battery, memory and leak tests, always-on/lockdown. Do not describe this as a working Android firewall.
